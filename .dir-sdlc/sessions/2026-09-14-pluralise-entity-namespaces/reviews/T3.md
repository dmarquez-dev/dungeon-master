## The finding this task exists for

**`dotnet ef migrations has-pending-model-changes` is blind to a consistent CLR-namespace rename.**

c5's literal single-site injection **was** detected — which satisfied the criterion as written and would have licensed a confident green. T3 instead observed that changing one of the three sites naming `…Dungeon.Dungeon` leaves `HasOne(…)` and `Navigation(…)` implicitly defining a second, table-less entity type, so detection was **overdetermined by a structural split** rather than by the name change. The reviewer confirmed the reasoning: `MigrationsModelDiffer` diffs the relational model, where identity is the mapped table, and an unreferenced bare entity type is a genuine structural difference.

T3 then probed the real edit's shape — all three sites renamed consistently — and got **NOT detected** (`No changes have been made to the model since the last migration.`, exit 0). Artifact `T3-ef-model-check.md:105-126`.

**The BEFORE control corroborates this independently and at full scale**, and T3 undersold it: at BEFORE the live model was fully plural (T1/T2 landed, Infrastructure's usings fixed) while all 48 snapshot strings were still singular — and the check reported no changes. That is a 48-occurrence, four-file demonstration of the same blindness, obtained before any injection. Artifact `:39-54, 130-132`.

**Why this sharpens trap #3.** The contract *did* establish this instrument — `.dir-sdlc/backlog.md:40` records it working in this repository, and the criterion mandated a positive control. Both were satisfied and both were misleading, because **the positive control injected a different defect class than the one under test.** A control must fail the way the real thing would fail, not merely fail.

## `contradicts` finding — T3's own recommended backstop

**Claim falsified:** `artifacts/T3-ef-model-check.md:138-140` — *"The runtime half — a real model built over SQLite — is T6's, per `migration-snapshot.md` §6."*

T3 escalated on evidence quality and recommended relying on T6's SQLite tests. **They are not independent coverage.** Since EF Core 9 — and this repo is on **10.0.11** (`Directory.Packages.props:22-23`) — `Migrate()`/`MigrateAsync()` throws when the model has pending changes against the migrations assembly's snapshot (`RelationalEventId.PendingModelChangesWarning`). So `SqliteInMemoryTestBase.cs:33` **does** load and diff the snapshot at runtime — but it runs **the identical differ**, which T3 demonstrated twice over is blind to a consistent rename.

**This also corrects the orchestrator's mechanism.** The orchestrator had reasoned that `Migrate()` only executes `Up()`, which contain zero namespace occurrences, so the tests never read the snapshot. That step is wrong; EF resolves the snapshot by type discovery rather than by a call site, which is why grepping for `BuildTargetModel` outside `Migrations/` found nothing. **The conclusion survives on stronger footing:** no automated check verifies the 48 strings — not the build, not `has-pending-model-changes`, and not T6, which is the same blind instrument rather than a second one.

## How the residual risk was actually closed

The reviewer closed the gap further than T3 did. T3's positive evidence stopped at 0 singular / 48 plural. Stronger evidence was available: there are only **four distinct strings** across all 48 occurrences, and each resolves to a type that exists. Verified independently by the orchestrator:

```
  8 DungeonMaster.Domain.Entities.Areas.Area          → Entities/Areas/Area.cs           namespace …Entities.Areas;
 12 DungeonMaster.Domain.Entities.Dungeons.Dungeon    → Entities/Dungeons/Dungeon.cs     namespace …Entities.Dungeons;
 20 DungeonMaster.Domain.Entities.Floors.Floor        → Entities/Floors/Floor.cs         namespace …Entities.Floors;
  8 DungeonMaster.Domain.Entities.Floors.PlacedObject → Entities/Floors/PlacedObject.cs  namespace …Entities.Floors;
```

Summing to 48. **`PlacedObject` correctly lands in `Floors`, not a `PlacedObjects` namespace** — the one spelling a mechanical "append an s" could plausibly have got wrong. Every distinct string is verified against the type it names, so the string-correctness question is **closed statically**, and the cost of an error was documentary rather than behavioural in any case (the differ pairs by mapped table, so even a consistently wrong name yields no spurious migration).
