instead of the specified three-site one: `handler.HandleAsync(typed, ct)` → `new CancellationToken(false)`
at `Dispatcher.cs:172` **only**, leaving `:139` and `:205` untouched.

## Escalation E1 — A15's prose contradicts the convention it cites

The reviewer declined to rule, correctly. The orchestrator then measured the convention across all three
test projects rather than accepting either reading:

```
type declarations immediately preceded by </typeparam> or </param>: 20  (13 files)
type declarations immediately preceded by </summary>:               98
```

Four of the 20 are T1's own. **Sixteen are pre-existing, across twelve files** — including
`DispatcherTests.cs`, the very file A15 cites as the convention, at `:231-243`, where the doc block for
`RecordingBehavior<TRequest,TResponse>` ends with `</param>`.

So A15's prose is not ambiguous; **it is wrong about the repository**. The convention is that a type is
*documented*, with `<summary>` first and `<typeparam>`/`<param>` after — which means the last line before
a generic or primary-constructor type is not `</summary>`. A15's own falsifiability command, scoped to
`[Fact]` lines, encodes the true convention; its prose over-generalised from six `[Fact]` to "every type"
without re-measuring.

This is the project's recurring failure mode in its exact form: **a universal is a count without a digit
in it.** The architect validated "every one of the six `[Fact]` in `DispatcherTests.cs`" — true — and then
extended the requirement to a population it had not counted.

Ranked options as the reviewer worded them, re-ranked by the orchestrator against the census:

1. **Amend A15 to scope the `</summary>` requirement to `[Fact]` methods and to type declarations with no
   type parameters or primary-constructor parameters; accept both files unchanged.** Rationale: the
   criterion's own falsifiability command already encodes this scope, and the census shows 16 pre-existing
   declarations that the unamended prose would condemn. Evidence: `repo` —
   `DispatcherTests.cs:231-243`, plus the 13-file census above.
2. **Accept A15 as met on its falsifiability command alone**, treating the command as operative and the
   prose as loose. Same outcome for the code; weaker as precedent, because it lets a criterion's prose and
   its command diverge silently and leaves the wrong prose on the record. Evidence: `repo`.
3. **Reorder the four doc blocks so `<summary>` follows `<typeparam>`.** Satisfies the letter. Contradicts
   16 pre-existing declarations, and reads as malformed to a documentation generator. Not recommended by
   either the reviewer or the orchestrator. Evidence: `judgment`.

## The reviewer's own assessment of the amendment it was handed

Asked explicitly whether the amended criterion had become vacuous, and told that a finding against the
amendment was worth more than a clean verdict, it returned: **not vacuous, but clause 2 is materially
weaker than clause 1, and here is by how much.** Clause 1 fixes the *position* of the summary, so it
fails on a missing comment, on an interposed attribute or blank line, and on any reordering; 20 of the 24
checked sites rest on it. Clause 2 constrains only the block's first line — it still fails a generic type
with no summary, or one documenting `<typeparam>` before `<summary>` (the shape option 3 proposed, so not
hypothetical), but says nothing about what follows; 4 sites rest on it.

Its verdict on the trade: the amendment gave up precision on 4 parameterised sites and was right to,
because the original clause "was not strict — it was false, and enforcing it would have required changing
conforming code." No objection on the merits; the reservation is finding 4, about enforcement rather than
content.
