## Advisory findings

is the sharpest criterion-authoring finding of the session, and it is a defect the orchestrator's Gate 2

`startRef`, and this one is about an assertion that cannot fail *after* it is written.

`DetailViewModelSources()` (`:188-196`) projects the 4-element literal array `DetailViewModelFileNames`
through `Select` with `File.ReadAllText`. **It yields exactly 4 tuples or throws
`FileNotFoundException`** -- so `.HaveCount(4)` can never be false. And the `RepoPaths.cs:52-55`
rationale C10 quotes is about `AppSourceFiles` returning an **empty list**; this test never calls
`AppSourceFiles` -- it composes paths with `RepoPaths.AppRoot` and `Path.Combine`. Three defects in one
criterion: a cited vacuity mode that does not apply to the implementation chosen, a required assertion
that cannot fail, and (per AD3) a grep form that cost a failure message.

**The scan is nonetheless genuinely non-vacuous -- by the throwing read, not by the asserted count**,
which is why the reviewer ruled C10 met. It also notes the shape matches the neighbouring
`FailureIsSurfacedTests.cs:210-217`, which has the same always-4 property, so this is the repository's
existing pattern rather than something T3 invented.

**AD2 -- residual vacuity the guard does not close: an emptied source file.** A source truncated to
zero bytes would still be counted (4) and would flag nothing, because this fact asserts only absence.
`FailureIsSurfacedTests` is immune, since it asserts positive routing content, so cross-coverage in the
suite catches it today. Asserting each `Text` is non-empty would close it locally in one line.

**AD4 -- the detector is clean repo-wide, so widening its population would be free.** The reviewer ran

## The regex, tested adversarially -- what it misses

The reviewer ran the exact pattern over **23 constructed forms**. It correctly flags the removed
sentinel, the reversed operand order, `!= default`, `== default(Guid)`, a ternary, a `switch` `when`
arm, and both a `this.`-qualified and a chained receiver; it correctly rejects all three near-misses.

Forms it **misses**, beyond the multi-line case the implementer disclosed:

| Missed form | Why |
|---|---|
| `if (addResult.Value.Equals(Guid.Empty))` | no `==`/`!=` operator |
| `if (Guid.Empty.Equals(addResult.Value))` | same |
| `if (results[0].Value == Guid.Empty)` | receiver is an indexer, not an identifier |
| `if (GetResult().Value == Guid.Empty)` | receiver is a call |
| `var id = addResult.Value; if (id == Guid.Empty)` | comparison is on a local copy |
| `if (addResult.Value == new Guid())` | `new Guid()` is neither `Guid.Empty` nor `default` |
| `if (addResult is { Value: var v } && v == Guid.Empty)` | property pattern |
| `EqualityComparer<Guid>.Default.Equals(addResult.Value, Guid.Empty)` | no operator |

**None of this is blocking:** C5's scope is the comparison form the session actually removed, and C6's
must-match case is exactly that form.

**One false-positive shape worth naming:** the predicate keys on the *member name* `Value`, not on the
receiver being a dispatch result, so `if (someNullableGuid.Value == Guid.Empty)` on a `Guid?` would be
flagged wrongly. Not live today -- 0 flags across all 58 App source files.
