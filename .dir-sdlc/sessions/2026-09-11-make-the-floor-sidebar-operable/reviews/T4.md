## Advisory findings

1. **The fault-path behaviour change is IN SCOPE, and the better failure mode.** Moving a statement
   past an `await` necessarily makes it conditional on the await not throwing; retaining the old
   unconditional semantics would have required an added `try/finally`, **which is the extra choice,
   not the default**. Both call sites sit inside `catch (Exception exception) { _viewModel.ErrorMessage
   = …; }` (`DungeonDetailPage.xaml.cs:1471-1475` and `:1737-1741`), so a faulting reload now surfaces
   an error banner **and** leaves the shape the user just drew or moved on screen, rather than a banner
   over a blank canvas. Documented on the `clearPlaceholder` parameter and covered by
   `RefreshThenClearAsync_WhenTheRefreshFaults_LeavesThePlaceholderOnScreen`. This was the task's single
   judgement call; no action needed.
2. **The margin is thin enough that "unreachable" must not be read as settled.** Max 16.62 ms is
   0.08 ms — **0.5%** — under the assumed 16.7 ms interval, and the probe constructed handlers directly
   rather than going through `CommandDispatcher`. The reviewer confirmed all three production calls in
   `ViewModels/MapCanvasViewModel.cs:189-233` go via `dispatcher.SendAsync`, so pipeline overhead is
   genuinely excluded and the number is a **floor**. T4 disclosed both, which is what c3 requires — the
   note is for whoever decides `MASTER-166`'s disposition, not a defect in T4.
3. **The measurement is not reproducible: the probe was deleted.** Confirmed — grep for
   `OptimisticGhostLatencyProbe|GHOST_PROBE_DIR` over `src` excluding `obj` returns nothing, and there
   is no stray `.db` outside `bin`/`obj`. Acceptable for a temporary probe, **but worth preserving the
   probe source in the session artifacts if the number is going to be cited later.**
