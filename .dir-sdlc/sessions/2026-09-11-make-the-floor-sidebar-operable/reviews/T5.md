## The three judgement calls, adjudicated

**1. c7 — starting the server SATISFIES it; it does not circumvent it.** c7's condition is that the
server, Developer Mode and a built exe are all present. **A built exe is itself the product of a
documented setup step** (`README.md` §1) and nobody would call running that a workaround; `README.md`
§2 — "Start the Appium server … leave it running" — is the same kind of step in the same procedure c1
required T5 to read first. c1's "never worked around, never assumed present" governs the four-row
**version** table, all four of which were present and checked; substituting a different driver version
would be the workaround it guards against. **Decisive:** c4 independently requires T5 itself to
demonstrate the asymmetry by disabling the driven step and quoting the split, which no fallback reading
makes possible — **the strict reading makes c4 and c7 mutually unsatisfiable.** The reporting half of
c7 was honoured exactly: which item, and by what check.

**2. Units — sound, and the same choice T3 made.** The threshold is applied in the **weaker**
direction: measurement is `DIU x 1.25`, so asserting `pixels >= 23` is implied by the real requirement
`DIU >= 23` and never the reverse. A DPI change can therefore never redden these without the defect
genuinely returning — the property a ratchet needs. c3(b) says "at least 23 by 23" without naming
units; c3(c) says "at least the number T3's report states", and T3 stated 14 having measured 23 for
precisely this reason.

**3. `EditDungeonButton` — inside the rule.** c5's trigger is *adding* an id and *editing* a `.xaml`;
C2 §1 reads "If `T5` needs an `AutomationId` that is not in this table, it escalates; **it does not add
one**" — the prohibited act is the addition. Reviewer verified the id predates the session:
`git show 280c700:…/DungeonListPage.xaml` carries it at line 63.

## Advisory findings

1. **"Last match wins" is not guaranteed in general, but it FAILS SAFE, which is what makes it
   acceptable** (`UiaFocus.cs:48-61`). Correct only because the spurious `HasKeyboardFocus="True"` node
   is an **ancestor** of the real one and serialized UIA page source is pre-order. A false positive in a
   later sibling subtree would defeat it. **Not blocking because every wrong answer it can give is a
   wrong id**, so the walk's `Should().Contain(...)` goes red rather than green — the reader cannot
   manufacture a pass, only a false failure, which the named control then separates. Selecting the
   deepest match by nesting depth would remove the assumption.
2. **The DIU-threshold-on-pixels choice weakens the ratchet above 100% scale.** At 1.25 the toggle
   assertion effectively demands 18.4 DIU where C3 pins 23, so a genuine regression to 20 DIU would pass
   on this display. Documented by T5; the harness cannot read the scale factor out-of-process. Deriving
   it from a known-fixed-size element would recover the true unit without new instrumentation.
3. **`//*[@AutomationId='FloorCard'][1]/..` is a per-parent predicate, not a global one** (`:95`) — it
   relies on `FindElement` returning the first match rather than on the predicate being selective. It
   resolves correctly and its control guards the way it could go wrong. Readability note only.
4. **Fact (b)'s control shares the `MinimumToggleEdge` constant with the fact it controls** (`:104`,
   used at `:191` and `:293`). The asymmetry holds for the failure mode that matters, but a future
   change to the constant moves both arms together.
