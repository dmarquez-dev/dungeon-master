## The evidence demotion, which is the most important thing in this review

**"Each injection failed only its own test" is close to tautological, and it was being read as much stronger than it is.** Reverting a site to a per-call `AsReadOnly()` body changes reference identity and **nothing else** -- behaviour, counts and contents are unchanged. Since each test's `BeSameAs` touches only its own property, exactly one failure per injection is the arithmetically expected outcome. What the result actually establishes is the narrow fact that no test accidentally asserts a neighbour's property. It is **not** evidence of pinning strength.

No setup is shared in a way that could mask: xUnit constructs a new class instance per test, so each test gets its own `SqliteConnection`, its own migrated database, and builds its own aggregates. There is no shared mutable state. The one informative row is `Area.Outline`, which failed 2 of 2 as the design predicts.

**The implementer's stronger inference is a non sequitur.** It argued that the `Floor.Objects` injection going red "on an empty collection" independently rules out the shared-empty-singleton failure mode. It does not: that injection restores per-call `AsReadOnly()`, which fails `BeSameAs` whatever the contents, and says nothing about whether the test would reject a wrapper not bound to *this instance's* `_objects`.

**The orchestrator repeated the overstatement to the user before this review returned, and it is corrected here.**

## Advisory findings

### A1 -- `Objects_ReadTwiceOnTheSameFloor...` is the weakest of the five

`:87-100` reads an **empty** collection and carries no count or content assertion, unlike its four
siblings. It would therefore pass against a shared or static empty read-only singleton -- the exact
failure mode criterion 3's rationale names. **Cheapest close: place one object and add `HaveCount(1)`,
matching the other four.**

### A2 -- nothing asserts the cached wrapper stays live after first read

`_outlineView ??= _outline.ToList().AsReadOnly()` -- a cached **snapshot** rather than a view -- passes
all seven tests, the EF one included, because every read happens after the only mutation. Production is
safe only **incidentally**: `AreaMethods.cs:51-52` mutates in place (`_outline.Clear()` then
`AddRange`) rather than reassigning. A read-mutate-reread assertion would pin that, and without one the
guard does not cover the property it most needs to.

### A3 -- no cross-instance assertion

Two instances must not share one wrapper. Low value for the four `readonly`-field sites, where CS0236
makes an instance-field capture impossible to hoist to static, but it is the residual hole behind A1.

### A4 -- six of seven tests pay a `Database.Migrate()` they do not use

A time cost and a diagnosis cost -- a fixture-constructor fault reddens all seven rather than one -- not
a correctness cost. See the fourth question below.

### A5 -- the implementer's "6 `BeSameAs` across 5 files" rests on a substring match that also hits `NotBeSameAs`

The conclusion is unaffected either way.

## Answers to the four questions put to the reviewer

**Discrimination and the injection result:** covered above -- they discriminate for their stated claim,
but the per-injection arithmetic is expected rather than informative.

**Does the EF test genuinely reach materialisation?** Yes, and the reviewer verified the mechanism rather
than accepting the report. `CreateFactory()` returns `new UnitOfWorkFactory(new TestDbContextFactory(Options))`;
`CreateAsync` calls `CreateDbContextAsync`, and `TestDbContextFactory.CreateDbContext()` is `new(options)`
with **no pooling**. So the second unit of work holds a brand-new `AppDbContext` with an empty change
tracker, and the seeding one is disposed at `:166` before it opens. The only thing shared is the
`SqliteConnection`, which carries rows rather than tracked instances. `loaded!.Floors.Single().Areas.Single()`
is therefore a freshly materialised `Area` whose `_outline` is the list the value converter installed
after `private Area()` ran -- precisely the path criterion 5 names. Nothing short-circuits it.

**A wrong implementation that passes everything:** two, both in the advisory list -- the cached snapshot
form, and a shared static empty singleton for `Floor.Objects`. **The positive control closes neither**: it
proves `List<T>.AsReadOnly()` allocates per call, not that any given property's wrapper is bound to that
instance's backing list.

**Does the single-class / `SqliteInMemoryTestBase` choice cost correctness?** No. The base opens a private
in-memory connection and migrates per test instance; the six in-memory tests never touch a `DbContext` and
construct domain objects directly, so an inherited migrated database cannot change their outcome -- no
ambient context, no seeded state, no static the fixture mutates. The costs are time and diagnosis only.

## On the deliberately omitted re-materialisation hazard test

**Correctly out of scope, and the reasoning is sound.** Criterion 5 asks for the materialisation path plus
an explicit statement of coverage; both were delivered. The hazard -- `_outlineView` cached over list A,
then EF installing list B onto an already-read `Area` -- is genuine, but reaching it requires reflection
onto `_outline` to observe the stale wrapper, and a **passing** test there would enshrine the stale read
as intended behaviour, which is the wrong artefact to commit. No criterion required it. It belongs on the
audit index as a follow-on.
