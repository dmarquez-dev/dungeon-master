## Advisory findings

### A1 -- the `awk` CRLF detector is blind in this shell, and its numbers are unreproducible

The implementer reported `total_lines=3, crlf_lines=3, non_crlf_lines=0`. The reviewer gets the exact
inverse on the same, correct file. **The orchestrator reproduced the reviewer's result**: with
`GNU Awk 5.3.2`, `awk '/\r$/ {c++}'` returns **0** on a file `cat -A` proves is fully CRLF, and
`awk '{print length($0)}'` returns `47, 0, 61` -- content lengths with no CR in `$0`. The CR is stripped
before the pattern sees it.

**The detector reports a passing file as failing**, which is the dangerous direction. It changes no
verdict here, because criteria 2 and 3 name `cat -A` as their evidence and `cat -A` is correct and
reproducible. **The awk form must never appear in a criterion.** This is a new entry on the standing
instrument-trap list, alongside `grep -P` erroring while printing 0.

### A2 -- criterion 2's own rationale carries a wrong size

The frozen rationale says "this ~95-byte file". Measured: **114 bytes** in the working tree
(`wc -c`), **111 bytes** in the blob (`git show 00a093a:... | wc -c`). 111 plus three line endings is
114. The figure is load-bearing on nothing -- the rename-similarity conclusion holds at any of these
sizes -- so this is advisory and not a `contradicts` finding. It is still a figure that reached a frozen
artifact without a command beside it.

### A3 -- "byte-identical at `00a093a`" is ambiguous between blob and working tree

The stored blob is 111 bytes LF; the new working file is 114 bytes CRLF. They are not byte-equal **as
blobs**. Everyone involved used the working-tree reading, which is the one that makes the criterion
meaningful. The ambiguity is benign and in fact favourable: because the index normalises to LF, the
committed blobs will be identical, so **rename similarity at commit time is 100%, not merely above
threshold**. Worth stating explicitly in any future criterion of this shape.

## On the predicate control

The implementer wrote a near-miss control -- `printf 'a\r\nb\nc\r\n'`, two CRLF lines and one LF-only
line -- and reported the detector flagging the LF line. **The control's shape was right and its verdict
was not.** A lone LF among CRLF lines is a strictly harder instance than the defect under guard, since
`sed -i` converts the whole file and the real defect presents as 3-of-3; a detector resolving 1-of-3
necessarily resolves 3-of-3. But the reviewer ran that same control here and got `3`, the identical
answer the correct file returns -- the signature of a predicate reading nothing.

The instinct was exactly right: a detector returning 0 proves nothing until shown able to return
non-zero, and it is why this was findable at all. The lesson is narrower and sharper: **a control that
passes under an interpreter the reviewer cannot reproduce licenses nothing.**
