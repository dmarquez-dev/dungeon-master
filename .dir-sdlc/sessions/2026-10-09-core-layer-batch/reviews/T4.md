## Advisory findings

### A1 -- `_outlineView ??= …` is not thread-safe, so the comment's "at most once per Area" is a universal the code does not guarantee

Two concurrent first reads can each evaluate `_outline.AsReadOnly()`, the later write winning, yielding
two wrappers over the same list. Harmless for contents, but it breaks reference equality between those
two reads and falsifies the wording. Domain entities here are not documented as thread-safe and nothing
in the repository reads `Outline` concurrently, so this is a wording fix rather than a behaviour fix.

### A2 -- the lazy cache goes permanently stale if `_outline` is ever replaced after a first read, and no existing guard would see it

**Measured, not reasoned.** The reviewer swapped `_outline` for a new list by reflection *after* a read
and `Outline` still returned the wrapper over the old list (`HAZARD PROBE: ... = True`). It is
unreachable today: `grep -rn "\.Reload()\|CurrentValues.SetValues"` over `src` returns no hits, and
`grep -rnE "_(vertices|floors|areas|objects|outline)\s*=[^=]"` returns only the five field initialisers.
So the comment's "First read always follows materialization" is true of the current code but is an
unqualified claim about re-materialisation nothing has tested. The invariant worth stating is
"`_outline` is assigned at most once per instance" -- which is precisely what a future `Entry.Reload()`
would break.

### A3 -- two anchors in the implementer's report are false against the post-change tree

It reported `OutlineComparer` at `AreaConfiguration.cs:28` and its wiring at `:101`; the true lines are
`:37` and `:110`. This is the drift class the session exists to repair, but the numbers live only in a
report, no repository file carries them, T6 re-derives its citations independently, and criterion 12's
amended text states its requirement as preservation of the comparer alone. **The orchestrator caught
both independently before the review returned.**

### A4 -- the new comment's first paragraph states a counterfactual that was reasoned, not measured

`AreaConfiguration.cs:19-23`, "the original symptom … is therefore gone", describes what reference-equality
fallback would now do, which no run exercised. It is sound, and `CommitAsync_AfterLoadingAnUnmodifiedArea_WritesNothing`
passing is consistent with it -- but that test passed before the change too, so it is not evidence for the
clause. The second paragraph, by contrast, is measured and says so.

## On the four questions put to the reviewer

**Criteria 6 and 8 under the amended text:** met cleanly. It checked the constructor chaining rather than
assuming it -- grepping every partial file of `Dungeon`, `Floor` and `Area` found no constructor outside
the two in each primary file, so no path reaches a null view field. On the CS0236 point, the amended text
itself names "the constructor-assigned readonly form this criterion prescribes", so constructor
assignment is the governing reading and no interpretation was required.

**The scratch harness as evidence for criteria 1-5:** adequate, and the reviewer did not take T4's word
for it -- it built its own against the same two built DLLs, got `sameAs=True` at all five sites, and saw
its pre-change control print `False`. Two things make the evidence stronger than its disposability
suggests. For the four readonly sites, the property is a bare read of a field assigned exactly once, so
reference equality is a language guarantee visible in the diff and the harness confirms rather than
establishes it. And the EF-materialised path is already covered by committed code:
`AreaOutlineChangeTrackingTests.cs:92` traverses `loaded!.Floors.Single().Areas.Single().Outline` through
both cached wrappers on EF-materialised instances and finds three segments, which an orphaned wrapper
could not do. The durable-guard gap is real and is exactly what **T7** exists for; it is not a T4 defect.

**Whether the lazy form hides a defect the guards cannot see:** one, advisory A2, currently unreachable.
The three shapes specifically looked for are all absent: caching before materialisation cannot happen
because `Outline` is only reachable once EF has handed the entity out and `PropertyAccessMode.PreferFieldDuringConstruction`
keeps construction on the field; `SetOutline` mutates in place (`AreaMethods.cs:51-52`, `Clear()` then
`AddRange`), so a genuine edit flows through the cached wrapper; and no path anywhere in `src` reassigns
any of the five backing lists. **The structural consequence worth recording is that the comparer's role
has inverted**: before this change its absence caused spurious writes, and after it its absence silently
drops outline edits. The new comment says so.

**Criterion 11's comment accuracy:** correct on every checkable claim, with the one soft spot at A4. It
embeds its command rather than a bare figure, which is the right form.

## A contract-class finding outside the review's scope

The reviewer flagged an untracked file at the **worktree root** whose entire name was a flattened
absolute scratch path ending `...gitT2-extracted-message.txt`, attributing it to the git agent's T2
handling rather than to T4. **The orchestrator confirmed and removed it**: 2920 bytes, sha256
`6d6c14d1329c9411294f2049fd58c1a574fb98b6800f0cb025e69adabc698da5` -- byte-identical to the authored T2
commit message, with **0 CR bytes**, so it was a scratch artefact written to the wrong place. `:` had been
mapped to U+F03A, as Git Bash does when a Windows path is used as a filename.

Two things follow. A write landing in the worktree root instead of a scratch directory is the
contract-violation class, and **the orchestrator's own ownership sweep missed it** because that sweep
examined tracked modified files only; `--untracked-files=all` is what finds it. And the file's zero CR
bytes independently corroborate that `dir-git`'s later claim about git storing commit messages with CRLF
was false.
