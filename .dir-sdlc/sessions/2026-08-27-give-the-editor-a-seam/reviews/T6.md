## Contradicts

**C1 — Criterion 5's "so the binding compiles" is false, and the same assumption is written into the frozen contract.** `manifest.json:211` and `contracts/app-detail-view-models.cs:87-91` both rest on the root `x:DataType` making view-model bindings compile. That holds for `Dungeon` and `ErrorMessage` — `[ObservableProperty] public partial` properties whose declaration exists in user source, so MAUI's generator sees them — but **not** for `GoBackCommand`, which `[RelayCommand]` emits with no user-source declaration at all.

1. **(best) Record the discriminator in the contract, not just the failure.** Amend the contract comment to say CommunityToolkit members are visible to MAUI's binding generator only when a user-source declaration exists (partial property); wholly-generated members (`[RelayCommand]`) are not. Turns a per-site surprise into a rule an author can apply *before* writing the binding. Evidence: `repo`. **Caveat: this does not explain `CancelCommand` going unreported at `CreateDungeonPopup`, so the rule is a strong heuristic, not proven complete.**
2. Leave the contract; carry the correction in the session log only. Evidence: `repo`.

## Advisory findings

**A1 — `.editorconfig:42` is cited wrongly in two tasks: a template defect, not two mistakes.** `:38-39` is `[*.xaml]` → `indent_style = tab`; `:41-43` is `[*.{json,yml,yaml}]` → `space`/`2`. T4 criterion 13 and T6 criterion 10 carry the **identical false citation, worded near-identically** — one criterion template propagated to two independently-dispatched tasks. No effect on either diff: both were told to match the file and not retab, which is correct regardless. The instruction is right; only its authority is misattributed.

**A2 — the repo's XAML actually violates its own `.editorconfig`.** `[*.xaml]` mandates tab, yet `DungeonDetailPage.xaml` has 0 tab-leading and 643 space-leading lines, and `CreateDungeonPopup.xaml` is likewise space-indented. `IDE0055` is a C# analyzer and does not police XAML, so nothing enforces it. Worth a decision — fix the `.editorconfig` section to `space` to match reality, or retab the XAML — but not in this task.

**A3 — `SemanticProperties.Description="Dungeon notebook"` is thinner than its sibling.** The `MapCanvas` pair (Description + Hint) tells a screen-reader user what the surface is *and* what to do with it; the `Notebook` gets a two-word noun and no Hint, for a view that spans every row of the outermost grid when shown. Criterion 3 asks only that it be announced, so this is met — but a Hint would serve the same user better.

**A4 — `Level2` for the FLOORS caption is the right choice.** The criterion says only "carries `SemanticProperties.HeadingLevel`", so any level satisfies it literally; T6 picked the one that makes the hierarchy coherent, since T5's committed code-behind sets `Level3` on each floor row. `Level3` would have sat the caption level with its own rows; `Level1` would imply a page-level heading it is not. **Good judgment, and exactly the cross-file reasoning an under-specified criterion invites getting wrong.**

**A5 — the unconditional (non-`OnPlatform`) back behavior is correctly reasoned.** Gating would put macCatalyst — the one target nobody can run under ADR-001 — on a code path Windows never exercises, which is the opposite of what an unverifiable target needs. Sharing the exact path that *is* clicked on Windows is the strongest available evidence for the target that cannot be clicked.

**A6 — criterion 8's vacuous satisfaction is honest.** `BackButtonBehavior` derives from `BindableObject`, not `Element`, so it takes no `AutomationId`, and the affordance it configures is the host's own back arrow carrying the platform's accessible name and keyboard reachability. T6 added no interactive element and no colour, so there is nothing for the criterion to bite on. Declining to set `TextOverride` — which would alter rendered chrome on a target nobody can run — is the conservative and correct call.
