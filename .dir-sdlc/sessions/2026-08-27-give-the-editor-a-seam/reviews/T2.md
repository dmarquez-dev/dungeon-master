## Advisory findings

1. **T2's ray-flip reasoning is correct, and stronger than it claimed — not a coverage gap.** Verified empirically (`AreaOutlineGeometry.cs:157`, `x <` → `x >`, still 129/129) and analytically: traversing a closed polygon flips the `(y_i > y)` predicate an even number of times, so the spanning-edge count is always even; every spanning edge's intersection lies left or right of the test point, hence `left + right = even` and `parity(left) = parity(right)`. The `inside` toggle reads only that parity, so the two ray directions are **provably indistinguishable for any closed polygon** — not merely a simple one — except exactly on the boundary, which `ContainsPoint`'s own XML comment declares unspecified. No test could catch this mutation, and none should try.

2. **The `n < 3` guard is genuinely unreachable, and criterion 4 is still honestly met.** Reproduced (`n < 3` → `n < 0`, still 129/129): with n=0 the loop body never runs, with n=1 `y_i == y_j` blocks the toggle, with n=2 the same segment is walked twice and the toggles cancel. But criterion 4 asks the tests to pin the *behaviour*, not to kill the *guard statement* — and the three tests do go red against a real defect (`return true` inside the guard → 3 failures). The redundancy is a property of T1's implementation, not a T2 weakness; the guard is worth keeping as documented intent. Reporting it rather than hiding it was the right call.

3. **`SizeOf` stub is the right design, but one comment reads as a claim about real data.** `MapHitTesterTests.cs:283` maps `Chest → (2,2)` and `Bed → (4,4)`; the real `ObjectKindInfo.GetObjectSize` at `ObjectKindInfo.cs:35` gives `Chest => (0.65f, 0.65f)`. Harmless and correct — criterion 7 ranks on "the supplied `objectSize` delegate", the delegate **is** the seam, and App.Core cannot reach `ObjectKindInfo` by design. Relative ordering (Chest < Bed) matches reality. But the per-test comment at `:126` ("A 2x2 tile object at (100,100)…") reads as a statement of fact; a half-line noting these are stand-in sizes would close the ambiguity.

4. **`Guid.NewGuid()` is unseeded randomness, though not outcome-bearing.** Criterion 13's letter asks that randomness be seeded. No assertion depends on a Guid's value — the one place a value comparison mattered uses the fixed `AnotherAreaId` at `MapHitTesterTests.cs:14`. Deterministic in effect, which is why the criterion reads as met; a note in the report would make that explicit.

5. **`ResetDrawState_WithObjectInteractionInFlight_LeavesEveryObjectInteractionFieldUntouched` asserts 4 of the 8 object-interaction fields.** `MapEditorStateTests.cs:262` checks `SelectedObjectId`, `HoveredObjectId`, `PendingObjectClickId`, `ObjectDragAnchorScreen` — not `ObjectDragTargetCanvas`, `PopupBounds`, `IsObjectDragConfirmed`, `ObjectLongPressHandled`. The "InFlight" qualifier arguably scopes it to what the arrange step set, so not a criterion-11 breach — but reusing `FillObjectInteraction` and asserting all eight would make the name literally true and would additionally catch a `ResetDrawState` that nulls `PopupBounds`.

6. **The injected-defect count needed reconciling, and has been.** T2's report prose says 54; `injection-results.json` carries **69** result entries. The orchestrator verified directly: **69 entries, 1 with an empty `failed` list (so 68 effective), union of failing test cases exactly 129.** The 129/129 coverage claim does not depend on the empty one (`D30` covers the same test). **69 / 68 effective is the number of record; 54 is superseded.**
