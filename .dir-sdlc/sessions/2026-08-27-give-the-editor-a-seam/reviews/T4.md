## Advisory findings

**A1 — Criteria 2 and 12 are jointly unsatisfiable with `app-navigation.cs:47`, and this is a spec defect, not an implementation one.** The contract requires `ShellNavigationService` to be the one place that reads `Shell.Current`; the criteria then forbid any such read and demand a grep count that the mandated read, four explanatory comments, and one deliberately-out-of-scope page hit all break. **Any correct implementation fails the letter.** Lesson for criteria authoring: a grep-count criterion over a term that also appears in prose and in the very type designed to contain it cannot be a pass/fail gate.

**A2 — `.editorconfig` and the repository's XAML files disagree, and criterion 13's citation is wrong.** `.editorconfig:38-39` declares `[*.xaml]` → `indent_style = tab`; `CreateDungeonPopup.xaml` is 0 tab-leading / 114 four-space-leading, so the file violates its own config. T4 matched the file and retabbed nothing — the criterion's *instruction* was right even though its *rationale* was false. Advisory rather than `contradicts` because no scoped work changes: the never-retab rule produces the same edit under either reading. **Candidate for the master index as a standalone conformance item** (either retab the XAML or scope `[*.xaml]` to space).

**A3 — the `MAUIG2045` / `CreateCommand` diagnostic is the one claim not reproduced.** Reproducing it requires adding a root `x:DataType` to a worktree file, outside a reviewer's write budget. The recorded text is internally consistent and criterion 10 licenses a recorded partial result. Noted only so the record shows which claims were verified and which were read.

**A4 — unsubscribing only on a successful close is correct, but leaves one dormant edge.** If `CloseAsync` throws and the user re-triggers the *same* outcome (Cancel twice after a failed cancel-close), `[ObservableProperty]` suppresses `PropertyChanged` for an unchanged value, so no second close is attempted. The realistic path (failed create-close then Cancel) does change the value and does retry, and `CanBeDismissedByTappingOutsideOfPopup="False"` closes the dismissal path — so this is theoretical. No leak: both types are transient and co-terminal, and this is strictly better than the old code, which never unsubscribed at all.
