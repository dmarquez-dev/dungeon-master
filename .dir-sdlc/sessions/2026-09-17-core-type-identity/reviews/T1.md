## The finding worth keeping — the one-sided injection, caught before it could mislead

The criterion specified deleting the **whole** `kind` guard. The reviewer judged that insufficient and
**deleted each condition separately**, which is the stronger test:

- Removing `kind == ObjectKind.None` alone → facts (5) and (7) red, fact (6) **green**.
- Removing `!Enum.IsDefined(kind)` alone → fact (6) red, facts (5) and (7) **green**.

Each half therefore has its own covering fact, and neither is carried by the other. This matters because
`Enum.IsDefined(ObjectKind.None)` is `true`, so the two conditions are genuinely independent and a
whole-guard deletion would have reddened everything at once and proved only that *something* was load-bearing.
This is the same class of finding as 6b-vii's mirror injection, applied without being asked.

The validator injection reproduced as specified: deleting `.NotEqual(ObjectKind.None)` failed exactly
`Validate_WithNoneKind_ReturnsViolation` — *"Expected result.IsValid to be False, but found True"* — with
`IsInEnumAlone_AcceptsNoneKind_WhichIsWhyNotEqualIsLoadBearing` and all 8 domain facts green (1 failed,
16 passed of 17).

## Advisory findings

No options are attached: `dir-reviewer` supplies ranked options for blocking findings only.

1. **Fact (7), the ordering test, asserts `ParamName` but not `ActualValue`** —
   `ObjectKindGuardTests.cs:88-90`. Criterion 6's "every rejection test" sentence reads on it, but criterion 7
   item (7) specifies this test's assertion as `ParamName` only, and `ParamName == "kind"` already closes the
   wrong-reason risk criterion 6 names. The reviewer treated the narrower criterion as governing and proved
   the test discriminating by injection — it went red the moment the `None` condition was removed. Adding
   `.Which.ActualValue.Should().Be(ObjectKind.None)` would remove the ambiguity.
2. **The throwaway `KindIsInEnumOnlyValidator` would report `IsValid == true` even with its `RuleFor` line
   deleted** — `AddPlacedObjectCommandValidatorTests.cs:172-181`. An empty `AbstractValidator` accepts
   everything, so a green result does not by itself distinguish *"`IsInEnum` accepts `None`"* from *"no rule
   ran"*. The criterion prescribes exactly this construction, and domain fact (4) plus the existing
   `Validate_WithRotationOutsideTheEnum_ReturnsViolation` supply the mechanism independently, so the claim
   stands. A second assertion that the same throwaway validator *rejects* `(ObjectKind)999` would make the
   rule's presence self-evident. **This is a vacuity finding against a criterion the orchestrator wrote** —
   the construction was prescribed, so the defect is in the criterion, not in the implementation.
3. **Fact (2) checks only the first two members' ordinals** — `ObjectKindGuardTests.cs:22-24`. A reordering
   deeper in the enum would not be caught. Criterion 7 item (2) asks for exactly `DoorWood == 1` and
   `DoorIron == 2`, so this is in scope as written; asserting the last member's ordinal too would bound the
   whole range.
