## Blocking finding, and how it resolved

**Criterion 13's observation never reached the review.** The reviewer had the ADR and the criteria but
not the implementer's report, so the solution-build line was not in front of it. It declined to mark
met a criterion whose evidence it had not seen, and declined to run the build itself because the
solution now contains T1's live `DungeonMaster.App.Core` and `DungeonMaster.App.Tests` and building
it would write `bin/`+`obj/` into a concurrently-owned directory. Both refusals were correct.

Ranked remediation options, as the reviewer worded them:

1. **Have the implementer paste the build line it already observed.** Closes on one line of existing
   output, no edit to the ADR, no revision round. Evidence: `repo` — T1 has since restored, so a
   clean worktree solution build is achievable now even though it was not when criterion 4's build
   was relocated.
2. **Escalate the criterion as unreachable rather than revising T4.** If T4 hit `NETSDK1004` on the
   solution for the same reason it hit it on the App project, the proof lived inside T1's ownership
   and T4 could never have obtained it. Evidence: `repo` — matches the recorded pattern that a
   criterion whose proof lives outside the owning task cannot be met.
3. **The orchestrator runs the solution build once T1 reports done and records the line against T4.**
   Evidence: `judgment` — moves the observation to whoever can take it safely.

**Resolution: option 1, with the orchestrator independently confirming.** The implementer did run the
command and reported `Build succeeded. / 0 Warning(s) / 0 Error(s)` for
`dotnet build <worktree>\src\DungeonMaster.sln`. The evidence existed; the dispatch failed to carry
it. This is an orchestrator defect, not a defect in T4's work, and no revision round was spent.

The orchestrator then re-ran the command itself, after both reviews had completed and the worktree
was quiet, rather than closing the criterion on the implementer's word alone:

```
dotnet build src/DungeonMaster.sln
Build succeeded.
    0 Warning(s)
    0 Error(s)
Time Elapsed 00:00:06.37
```

That run includes T1's two new projects, which were not in the solution when T4 first observed it —
so it is stronger evidence than the original, not merely a repeat of it. Criterion 13 is **met**.

## Advisory findings

- **The ADR does not say which checkout produced its build evidence** (`docs/architecture-decisions.md:36-45`).
  In a record whose thesis is keeping verification claims precise, the provenance of its one
  observation is worth a clause. No criterion requires it.
- **The implementer's justification for relocating the build is inaccurate.** It argued the App source
  is byte-identical between worktree and main checkout at those paths; `diff -rq -x bin -x obj` shows
  `DungeonMaster.App.csproj` and `packages.lock.json` differ, by T1's added `ProjectReference`. Every
  `.cs` file is identical and `TargetFrameworks` is unchanged, so the conclusion survives but the
  stated reason does not. Criterion 4 is unaffected: the ADR's diff base is `702ff76`, at which the
  App project is exactly the main-checkout version.
- **Four reported record defects confirmed, all correctly handled, none a finding against T4:**
  `UI-021`'s cited locations (294-301 / 445-451 / 935-941 / 1196-1202 / 39-41) are stale against the
  actual 329 / 516 / 1056 / 1313 / 46; `XCUT-004`'s platform list and its "nothing here can build the
  Mac one" are both refuted by the tree. The ADR uses current lines and corrects both on the record.
