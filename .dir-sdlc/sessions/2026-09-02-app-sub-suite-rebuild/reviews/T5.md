## Injection B -- reproduced independently, and the escaping trap guarded against by construction

T5's injection B **did not discriminate on its first run, and T5 caught that with a positive
control**: a plain `<Label Text="&#xE9FC;" />` that the old scan certainly did reach also failed,
because the `\b` in the reconstructed pattern had become a literal backspace (0x08) through shell
escaping. In T5's words: *"Had I not included the control case I would have reported a false
result."*

The reviewer rebuilt the old patterns verbatim from `1ea5394` and **dumped the pattern's character
codes before using it**:

```
PATTERN CODES: 60,40,63,60,101,...,41,92,98,40,63,60,...
HAS LITERAL BACKSLASH-B: True
HAS BACKSPACE 0x08: False
```

`92,98` is `\` `b` -- a real word boundary. It notes the trap is live: its own first attempt to write
the probe through a heredoc was rejected by the harness for embedding a control character.

With the pattern proven sound:

| fragment | old scan | new scan |
|---|---|---|
| **positive control** `<Label Text="&#xE9FC;" />` | **1** | 1 |
| `AutomationId="width > height"` before `Text` | **0** | 1 |
| `Text='&#xE9FC;'` | **0** | 1 |

> **This is the fourth inert injection in the session and the first caught by construction rather
> than by luck.** The positive control is what makes the two zeros mean anything: without it,
> "everything failed" and "the defect was detected" are indistinguishable. The session's rule was
> *run the injection before you write the criterion*; T5 sharpened it to **run the injection and a
> control that must pass**.

## Advisory findings

**A1 -- the class doc comment, and the criteria's own wording, overstate the pre-task failure.**
`SemanticDescriptionTests.cs:177-184` says the `char` cast truncated `U+1F6E1` to `U+F6E1` "and then
rejected anything whose `string.Length` was not 1 ... so the control was dropped from the scan
entirely and passed the ratchet undescribed." The reviewer's probe shows that is **not** what
happened for a hex entity in the pre-migration regex scan:

```
OLD decode of supp entity -> U+F6E1 len=1 oldIconOnly=True
```

Truncation produced a **length-1 private-use string**, so the old scan **reached** the control and
reported it under the **wrong codepoint** -- it was **misreported, not dropped**. A genuine drop needs
a form the old hex-only `CharacterEntity` regex could not decode: a literal supplementary character
in the source, or a decimal entity.

This is prose rather than behaviour, and the fact itself is sound -- within the XML-based class the
parsed two-`char` value is what `Length != 1` rejects. **The criteria inherit the same imprecision
("rejected outright", "dropped"), so this is not a deviation by T5.** Worth a one-sentence correction
to the remark, not a revision round.

**A2 -- the `DecodeCharacterEntities` identity-function observation; the reviewer agrees with T5 on
both halves.** Keeping the call was right: criterion 1 requires it, it keeps the class free of a
decoder of its own, and it is what stops the two-decoders-three-files-apart drift `MASTER-040` names.
Flagging the `Text="&amp;#xE700;"` edge rather than deviating from a frozen criterion was also right.

One point in favour of leaving it alone that strengthens the case: **the failure direction is safe.**
MAUI renders that source as the literal 8-character string `&#xE700;`, which is not icon-only, while
the scan would decode it to a glyph and classify it as one -- producing a **false offender, which
fails loudly**, rather than a missed control, which is the silent failure this task exists to remove.
Reachability verified: `grep -rn 'Text="&amp;#' src/DungeonMaster.App --include=*.xaml` -> exit 1.

**Recorded for a later session** -- as a note on `ThemeSource.DecodeCharacterEntities` itself, since
the same over-decoding applies to its `&amp;` -> `&` replacement on any already-parsed value, and the
exposure is shared by **every consumer that feeds it parsed XML rather than raw text**. Not T5's to
fix.

**A3 -- `PendingDescription`'s key spelling changed meaning silently.** Entries are now matched
against `ThemeDocument.RelativePath` (forward slashes) rather than `Path.GetRelativePath` output
(backslashes on Windows). T5 documented it at `:62-65`, and `EverySemanticAllowListEntryStillOffends`
now also fails an entry the scan does not reach (`:150-156`), which is a real improvement. The set is
empty, so there is no behavioural difference today; the note matters only if someone adds an entry
from memory of the old spelling.

## Correction to this task's own commit message

`de371fb`'s message inherited the imprecision advisory **A1** had just identified, and the record is
corrected here rather than by rewriting history. It says:

> "A supplementary-plane codepoint was truncated through a char cast over parsed hex, so U+1F6E1
> became U+F6E1 and **the control was rejected as multi-rune under the old string.Length test**."

Those two clauses cannot both be true of the same input. If the cast truncated `U+1F6E1` to
`U+F6E1`, the result is a **length-1** string, which the old `text.Length != 1` test **accepts** --
the control was reached and misreported under a codepoint it does not have. Rejection as multi-rune
is what happens to the **parsed** two-`char` value in the new XML-based scan, which is a different
input reaching a different test.

The commit's substance is right -- both failure modes are real, both are now unreachable, and the
migration is sound. Only the causal chain in the message is wrong, in exactly the way A1 describes,
and it is wrong because the criteria and the class doc comment said the same thing first. Recorded so
that a later reader taking the commit message as the account of `MASTER-040` is corrected by this
file.
