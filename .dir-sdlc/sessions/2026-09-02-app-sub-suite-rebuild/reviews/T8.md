## The reflection-reads-nothing proof, reproduced independently

Injection at `MauiPropertyTypeTests.cs:366`: the namespace filter replaced with
`"Microsoft.Maui.Controls.NoSuchNamespace"`. Result -- **2 failed, 10 passed**, both reflection facts
red:

```
Expected reached to be greater than 0 because a reflection check that reached nothing
passes exactly like a correct one. Microsoft.Maui.Controls resolved at run time as
10.0.0.0 / 10.0.41+d15964ef4f0a6d0740b655ba7c6be9b96be8b187, but found 0.
```

**This is the answer to the question the task existed to ask.** A hand-transcribed table replaced by
reflection is only an improvement if the reflection is shown to reach the framework; otherwise it is
the same vacuity trap in a new costume.

## The method finding, confirmed in both directions

T8 reported *"a prescribed-looking injection that certifies nothing -- found by running it."* The
reviewer confirmed both halves:

- Removing `"int->double"` from `WideningConversions`: **Passed! 10/10.** The injection certifies
  nothing, because no `x:Int32` token in the app binds to a `double`-typed property.
- Removing `"int->CornerRadius"`: **1 failed**, with a real violation --
  `Controls/DmCard/DmCard.xaml:15 -> RoundRectangle.CornerRadius is CornerRadius, but 'DmRadiusLoose' is declared int; MAUI drops the value and the property keeps its default`.

**The second time this session an injection that looked discriminating proved inert**, and the second
time it was caught by running it rather than reasoning about it.

## The six discrepancies, adjudicated

1. **Criterion 9's `38` is a line count including prose -- confirmed defective.** `DmTheme.cs:18` is `///		initialiser); a <c>BindableProperty.Create</c> positional default, which is itself a`. Comments blanked, both derived counts are **37**. The criterion's substantive demand (both counts derived, neither hard-coded, structured == plain) is met; its number is an error in the criterion.
2. **Criterion 5's "leave the property on its default" is not observable -- confirmed, and T8's claim is stronger.** Reproduced: replacing `var before = owner.GetValue(property)` with `property.DefaultValue` turns it red with `double->int: ... setting it changed the property from -1 (Int32) to 4 (Int32)`. MAUI's default is `-1`; the live implicit `Button` style has already set 4. **Asserting the default would fail over correct behaviour.** "Unchanged" is what "the value is dropped" actually means.
3. **Criterion 15's `:392` is stale; no duplicate and no translation layer survive.** `TokenBindingFixture` retains a private `XamlNamespace` const at `:73` but uses it only for `XName.Get("Name", XamlNamespace)` to read `x:Name` -- a namespace literal, not a second copy of the qualification rule, so `MASTER-138`'s divergence risk is not reintroduced.
4. **The namespace scope is right and documented as measured.** Without it the element-independent fact would fail over `Microsoft.Maui.Controls.Internals.GIFHeader.BackgroundColor`, an `Int32` field of a GIF decoder. **Correctly resolved by narrowing the scope rather than weakening the assertion.**
5. **Stale line citations in criteria 8 and 10 -- real but immaterial.** Every cited member is unambiguously identifiable by name, and `build-file-ownership.md` §6 already makes name-first the house rule. Belongs to the manifest, not to T8.
6. **Relocating the two regexes into `TokenBindingFixture` is required by criterion 8, not a liberty.** Both `internal static` in the same assembly and namespace; the only external reader is the fixture's own scan.

## Advisory findings

**A1 -- `MauiConversionMatrixTests.MauiVersion` (`:93-95`) reports only the assembly version**, which
is `10.0.0.0` and constant across MAUI 10 patches. Its sibling in `MauiPropertyTypeTests` also reports
the informational version, where the legible `10.0.41` lives. Criterion 4 is scoped to the reflection
test and is met; the matrix file's message is simply less useful on a version bump.

**A2 -- `AllSixCornerRadiusTrapPairsAreStillCoveredByName` compares two literals in the same file.**
That is what criterion 2 asks for, and it does catch a dropped entry, but **it establishes nothing
about the framework by itself**. The framework claim rests on
`EveryElementQualifiedPropertyTypeMatchesTheResolvedMauiAssembly`, which the reviewer verified reads
the assembly. Recorded so nobody later reads it as an independent alarm.

## A limitation the reviewer disclosed, and a process gap it exposes

**The reviewer was never handed T8's report**, so it could not confirm that criterion 11's per-test
evidence quoted a command and an observed failure for each of the 13 new tests. It drove **8** red
itself and resolved the remaining five toward met by inspecting their structure -- each is a direct
`NotBeEmpty`/`BeEmpty` on a value derived in the test, with nothing that could make it unfalsifiable.

That is an honest limitation, and it is an **orchestrator** gap rather than a reviewer one: the
implementer's report exists only in the dispatch thread, and nothing routes it to the reviewer.
Recorded here so the next session either persists implementer reports beside `reviews/`, or the
orchestrator relays the per-criterion evidence into the review dispatch.

The reviewer also could not reproduce T8's stated baselines (665 and 5), because T4's four files were
uncommitted and in flux -- but the part that is T8's own is verifiable and checks out.
