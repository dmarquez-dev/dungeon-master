## The driven interaction, and why its control matters more than its failure

**Clicked** `CreateDungeonButton`; **changed** — `OnCreateClicked` opens `CreateDungeonPopup`, whose
`DmPopup` chrome carries `AutomationId="PopupTitle"`; **asserted** — `PopupTitle` absent before (count
0) and reading exactly `New Dungeon` after.

The discrimination has the shape this session converged on. With the click removed the fact fails on
`NoSuchElementException` — **and the other two facts passed in that same red run.**

> That asymmetry is the evidence. This repository's `MASTER-159` was a **false defect report**
> produced by a DPI-broken pointer probe that never reached the control it aimed at. A UI probe
> reporting nothing may have failed to reach the app rather than found nothing, so the two passing
> facts are worth more than the one failing one.

`Appium.WebDriver` **8.3.2** proven against server **3.7.0** — three distinct session ids, elements

## Advisory findings

**A1 -- the README's "These tests only read it" is falsified: the app writes to the user's real
database on every launch.** Measured by the reviewer — hash `%LOCALAPPDATA%\DungeonMaster\dungeon-master.db`,
run **only** the read-only control fact, re-hash:

```
42d0f8fec55271cdd874866fd187c4e8  ->  2f18164b21ac55f750faf126961585b6
9 bytes, offsets 0x1fee-0x1ff9: an __EFMigrationsLock timestamp rewritten
cause: MauiProgram.cs:193 calls MigrateDatabaseAsync at startup
```

**T11's substantive claim holds and was verified** — `Dungeons` row count 2 before and 2 after, no
other table's count moved, so nothing the user cares about is created. But "only read" is not what
happens, and **the exposure the sentence hides is that a UI-test run applies pending EF migrations to
the user's real database.**

Not blocking: **no acceptance criterion mentions the database at all**, and the criteria-only rule
governs. The *risk* is adequately recorded — T11 found it unprompted and named
`MauiProgram.DatabasePathOverride` as an in-process static with no out-of-process seam, confirmed at
`MauiProgram.cs:31`. The *sentence* over-claims and should say the tests write no domain data **while
the app still opens and migrates the real database on launch**.

This is the mechanism Session 6a built specifically to keep test runs off that file, and **the Appium
layer bypasses it entirely.**

**A2 -- a comment/code mismatch that is not one.** `AppSession.Open()`'s remarks say the driver
documents lowercase `windows`, while the code sends `"Windows"`. Harmless — the driver README says
case-insensitive and the sessions opened — but a reader comparing the two sees a discrepancy that
does not exist.

**A3 -- one line of the red evidence reads false.** `DungeonListPageInteractionTests.cs:90` prints
`clicked CreateDungeonButton` unconditionally, so in the discrimination run it appears in the failure
output **even though no click occurred** — in exactly the output the contract makes load-bearing
evidence. Emitting it from the same statement as the click, or after it, would remove it.

## What the reviewer could not reproduce

**The process leak.** T11 reported one `DungeonMaster.App.exe` surviving the *failing* run with its
driver quit. The reviewer's red run — same injected defect, same exception from the same line — left
**0** app processes. **Nothing contradicts T11:** `using var session` disposes on the exception path
and `Quit()` normally closes the window, so the leak is evidently **non-deterministic**. The README's
wording is a measurement rather than an over-claim — it says the close is "not a guarantee", names the
date the survivor was measured, and tells the reader to check after a red run. **That is the correct
correction of T11's earlier "`Quit()` always closes the app", and it stands.**

**Test counts for the other three assemblies** were not measured — no T11 criterion turns on them, so
695 / 77 / 23 are attributed rather than verified here.
