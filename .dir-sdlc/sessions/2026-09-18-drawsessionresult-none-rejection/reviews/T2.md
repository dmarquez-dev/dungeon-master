### The B7 exit-code ambiguity, and how it was resolved

Identical in shape to T1's A2, and resolved the same way. B7 says the injected command "builds with
exit code 0 and reports exactly one test failed"; the observed **process** exit was `1`, because
`dotnet test` exits non-zero when any test fails. The build step itself succeeded with zero
diagnostics.

**The reviewer applied the reading that "builds with exit code 0" scopes to the build step**, whose
purpose in the clause is to prove no analyser rejects the injected code. Met on that reading.
Recorded so a later reader does not have to re-derive it.

**The implementer raised this rather than reshaping the run to satisfy the wording** -- as it did on
T1. Two tasks, two implementers, the same criterion-wording defect surfaced both times by the party
that could most easily have hidden it.

### Why B7 matters more than an ordinary injection

Under the deleted-arm defect, the exception **type and `ActualValue` both still matched** -- the
catch-all throws the same exception type with the same value. The failure was:

    Assert.Contains() Failure ... String: "Unrecognised draw session result. (Parame"...
    Not found: "No placement attempt was made."

**The `Message` assertion is the sole discriminator.** A test asserting only the type and the value
would have stayed green -- which is exactly what happened at the sibling site, where 6b-ix's reviewer
deleted the same arm from `MutationOutcomeExtensions.cs:77-82` and all 11 `MutationOutcome` tests
passed, `ToResult_WithNone_Throws` included (`backlog.md:373`). B4 was written to assert the distinct
message for this reason, and B7 measured that it works.

is never consumed unguarded. Worth a backlog item rather than a revision round.
