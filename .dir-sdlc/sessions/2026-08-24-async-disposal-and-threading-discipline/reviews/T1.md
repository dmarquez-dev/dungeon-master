## Ruling on the G2 deviation

**Declining a contract-change escalation was correct, and the scanner's behaviour is right.**

T1 changed no contract and changed no consumer's worklist — T3 and T5 still remove exactly the 16
lines the contract enumerates. What it resolved is an inconsistency *inside* the frozen contract: the
prose (`_ =`) disagrees with the contract's own grep (`"_ = "`), its stated count of 16, and its
enumerated line list, all three of which agree with each other. Choosing the reading under which the
rule is satisfiable, documenting it in `ScanG2`'s XML summary, and pinning it with
`ScanG2_WhenALineIsASwitchExpressionDiscardArm_ReportsNothing` is the best available compliance with a
definition that is not single-valued. Under the literal prose G2 could never go green, which would
make criterion 1 unachievable by anyone.

**No false negatives.** The reviewer checked specifically for discards the scanner would miss:
`grep -rnE "(^|[^A-Za-z0-9_])_\s*=" --include=*.cs src/DungeonMaster.App | grep -vE "_ = [A-Za-z]"`
returns exactly the six `_ =>` arms plus five `defaultValueCreator: _ =>` / `UIHoverGestureRecognizer(_ => …)`
lines that do not trim-start with `_ =` at all; `grep -rn "_ =" … | grep -vE ":\s*_ ="` returns one
line (`HandCursorBehavior.cs:78`, a lambda parameter, not a discard); `grep -rnE "^\s*_=" …` returns
nothing. Every line-start `_ =` in the layer is either one of the 16 genuine task discards or one of
the 6 switch arms, and the exclusion is `StartsWith("_ =>")`, which cannot swallow a discard.

## Contradicts — the contract's non-task-discard claim is false, and it makes T3's and T5's G2 criteria unsatisfiable as worded

`contracts/async-discipline-rules.md:102` states the rule as "trimmed form that starts with `_ =`",
and lines 108–111 justify the flat token ban with *"There is no legitimate non-task `_ =` discard in
the layer today, which is why the rule can be stated as a flat ban on the token."*

**The tree contains six**, verified by grep: `Assets/ObjectAssets/ObjectKindInfo.cs:67,109,129`,
`Behaviors/HandCursorBehavior.cs:119`, `Graphics/FloorMapDrawable.cs:411`,
`Views/DungeonDetailPage/DungeonDetailPage.xaml.cs:924`.

This moves scoped work, because those sites sit in owned files. `DungeonDetailPage.xaml.cs:924` is

has a trimmed form starting with `_ =`" — so **T3 cannot meet its own criterion as written** without

the same wording, though T5's three files happen to contain no arm. `FloorMapDrawable.cs:411` is T2's
and `HandCursorBehavior.cs:119` is T4's, so the same prose would flag both if either reviewer applied
it literally.

**Ranked options, as the reviewer worded them:**

## Advisory findings

- **A1 — The residual G2 gap is the contract's token rule, not T1's exclusion.** A discard written `_=Foo();` or mid-line (`if (x) _ = Foo();`) is invisible to both the prose and the scanner. Zero such lines exist today (`grep -rnE "^\s*_=" …` → nothing; `grep -rn "_ =" … | grep -vE ":\s*_ ="` → one non-discard). Worth a sentence in T7's Session-4 note so a later reader does not over-trust the guard.

No such shape exists in the layer today.

Gate 3 should state the arithmetic as `448 + 1 (T6) + 20 (T1) = 469` rather than the criterion's literal `448 + <added>`, which cannot close in a shared worktree.
