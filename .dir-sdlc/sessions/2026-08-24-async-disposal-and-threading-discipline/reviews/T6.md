## Ruling on the reshape question

T6 reshaped four LINQ chains to satisfy criterion 5's line-based rule, disclosed it, and declined to treat it as blocking. **The reviewer ruled the reshapes consistent with criterion 4**, on this reasoning:

- Extracting the query to a local in `GetSummariesAsync` / `GetDetailAsync`: `IQueryable` composition is deferred, so hoisting the chain produces the same expression tree and the same single execution. Nothing enumerates at the assignment.
- `LoadAsync` expression body → block body: signature unchanged; an `async` block body with a single `return await` is the same state machine.
- `FindAsync` collapsed to one line: pure whitespace.
- **`.FirstOrDefaultAsync(predicate, ct)` → `.Where(predicate)` + `.FirstOrDefaultAsync(ct)` is genuinely behaviour-preserving.** EF Core's predicate overload is not a distinct execution path — it composes the predicate as a `Where` before evaluating first-or-default, so both forms reach the same translated SQL. The `.Where` sits after `.AsSplitQuery()` and filters on the root `Dungeon`, exactly the position the predicate occupied, so include-splitting and eager loading are unaffected. The only static difference is that `query` is typed `IQueryable<Dungeon>` rather than `IIncludableQueryable<,>`, irrelevant because nothing chains a further `ThenInclude`.

Criterion 4 bars changes to signature, lifetime and behaviour, not to statement layout, and the reshapes were forced by criterion 5's own rule. The reviewer additionally checked the lifetime detail most likely to hide a defect: the two-statement `await using` form disposes the same instance at the same scope exit as the original single declaration, and no exception can occur between the two statements, so no window exists in which a context leaks.
