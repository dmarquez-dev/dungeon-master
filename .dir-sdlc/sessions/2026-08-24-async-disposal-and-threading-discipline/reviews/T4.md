## Advisory findings

**A1 — the cached-`InputSystemCursor` assumption: both lookups spent, cannot confirm either way, stated as belief rather than fact.** `HandCursorBehavior.cs:124-138`.

First-party docs confirm the shape of the concern: `InputCursor` is `public class InputCursor : System.IDisposable`, implementing `IClosable`/`IDisposable` with `Close()` and `Dispose()`; `InputSystemCursor` is `sealed`, `MarshalingBehavior=Agile`, `ThreadingModel=Both`; `UIElement.ProtectedCursor` is `protected InputCursor ProtectedCursor { get; set; }` and its Remarks cover only hit-testing and descendant precedence. **Nothing** in either page states that assignment transfers ownership, that an element closes the cursor it was given, or that an instance may be assigned to only one element. The docs neither bless nor forbid the pattern.

Three reasons the reviewer judged it not a defect and specifically not blocking:

- Criterion 2 **mandates** the cache — "one `InputSystemCursor` is cached per `BehaviorCursorShape`" — so no criterion is violated; the tie-break resolves to advisory.
- The pre-change code called `InputSystemCursor.Create` on *every* `PointerEntered` and `PointerExited` and closed none of them. Caching cuts never-closed instances from unbounded-per-event to exactly three per process. **On the disposal axis this is a strict improvement.**
- `Agile` / `ThreadingModel.Both` removes any apartment restriction on sharing the instance.

The residual risk, worded as belief: *if* WinUI closes the cursor when an element unloads or when `ProtectedCursor` is reassigned, a shared instance could be closed out from under other elements, surfacing as cursors silently going dead after some views are torn down. No documentation says it does this. The pre-change code would not have exposed it, since each element got its own instance — so this is a real, if unconfirmed, change in exposure, **and criterion 6 is exactly the observation that would have caught it.**

**A2 — a leftover `DungeonMaster.App.exe` (PID 29464) was holding the worktree's output directory open**, from a manual-observation run, causing 30 × `MSB3026`, 3 × `MSB3027`, 3 × `MSB3021` and zero compiler diagnostics on the reviewer's first build. Not T4's defect — criterion 6 required launching the app. **Resolved:** the orchestrator checked with `tasklist` after the review and no `DungeonMaster.App.exe` is running; the process has exited.
