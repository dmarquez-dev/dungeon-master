## Advisory findings

1. **Contract defect, not a code defect.** `domain-mutation-outcome.md` criterion 1 says "the eleven
   new Domain tests named in section 6"; §6's own table lists **fourteen**. The implementer delivered
   fourteen. Third miscount in this session's contracts -- a Gate 3 note on contract authoring rather
   than a revision.
2. **Criterion 7's wording is unachievable by an implementer** on a shared worktree while concurrent
   peers hold the test project red. It should be phrased as an orchestrator-verified, post-integration
   criterion. Same defect the T9 review raised.
3. **`AddArea_WithUnknownFloorId_ReturnsNull` invokes the mutating delegate twice** -- once inside
   `act.Should().NotThrow()` and once as `act()`. Harmless here (no floor exists, so both calls are
   no-ops), but re-invoking a mutator to read its value is fragile if the test is extended.
   `act.Should().NotThrow().Which.Should().BeNull()` would call it once.
4. **The file now mixes both `Touch()` spacing forms.** Contract §3 / `dotnet-format.md` §11 want a
   blank line before `Touch()`. Several touched methods keep the pre-existing tight form
   (`Dungeon.UpdateFloor`, `Floor.RemoveArea`, `Floor.UpdateArea`, `Floor.RemoveObject`,
   `Floor.UpdateObject`). These are unmodified lines carried through the diff, so not a regression.
5. **The orchestrator's two `!` edits are correct** -- independently checked. In
   `RemoveAreaCommandHandlerTests.cs:27` and `AreaPersistenceDiagnosticTests.cs:41` the preceding
   `dungeon.AddFloor(...)` guarantees the floor id resolves, so `AddArea` cannot return `null` and the
   suppression cannot mask a real miss.
