## Advisory findings

1. **The criterion's predicted error codes were wrong; the implementer was right.** Criterion 1
   mandates compiling against the **built assembly** and predicts `CS0272`/`CS0122`. The actual codes
   there are `CS1729` + `CS0200`, because from metadata a `private init` accessor reads as *absent*
   rather than *inaccessible*. The reviewer reproduced both variants independently:
   `T2-review\probe-asm\` (assembly reference) yields `CS1729`/`CS0200`; `T2-review\probe-src\` (same
   sources compiled into a peer assembly) yields exactly the predicted `CS0122: 'Result.Result()' is
   inaccessible due to its protection level` and `CS0272: ... the set accessor is inaccessible`, for
   both records. **This is a defect in the acceptance criterion, not in the work** -- the fifth such
   defect this session. The substance the criterion was after -- both object initialisers uncompilable
   on both records, from outside -- is demonstrated by either code set. The criterion's wording should
   be corrected for any session reusing these contracts as a template.
   *Note: the implementer ran **both** probes and reported both, rather than reporting only the one
   that matched its criterion.*
2. `ResultMessageTests.ForFailure_WithValidationCategory_ReturnsTheSummaryMessage` exercises the
   `Validation` arm only via the zero-errors fallback path. The populated-errors path is covered
   separately by `ForFailure_WithValidationErrors_JoinsEveryMessageOnItsOwnLine`, so coverage is
   complete -- but the first test's name reads as if it covers the category generally.
3. The duplication of five members and three factories across `Result` and `Result<T>` is the
   knowingly accepted cost of contract §2.1 (sibling records, not a hierarchy, because a base class
   cannot be `sealed`). **Explicitly not raised as a finding** -- recorded so a later reader does not
   re-open it.
