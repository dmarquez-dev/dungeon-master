## The nine-versus-six discrepancy

Both figures confirmed independently. The commit message reads "Replaces **nine** migrations with one InitialCreate"; the tree shows **six** identifiers before and one after. The reviewer went beyond the brief: `git log --diff-filter=D` over the whole migrations path shows `7a4bb2d` is the *only* commit that ever deleted a migration, so no earlier deletion makes nine defensible — **six is the only supportable number, and the record cites the right one.**

On handling: the record does not silently pick the convenient number, it picks the *verifiable* one, and its wording "the six migrations **then in the tree**" is the precise qualifier distinguishing a tree count from the message's count. But it never tells the reader the conflict exists, while quoting that same commit message two paragraphs later as authority. Advisory A1 — no criterion obliges a record to reconcile an error inside a source it cites.

## The S2 → S3 downgrade — reviewer's ruling

**Defensible, not self-serving.** Against the contract verbatim: S2 requires violating "an explicit Microsoft guideline or a documented `dm-conventions` rule", or boundary/disposal/async/threading misuse. The record's `microsoft` citation is the migrations-applying page, which describes a *mechanism* — it states no guideline the code violates, and no `dm-conventions` rule is in play. **S2's first clause was never well-founded and its second does not apply.** What remains after the rewrite — the decision living only in a commit message, no startup detection of unrecognised history, no drift check, the stale comment — is a documentation-and-provenance weakness, which is S3's definition almost word for word.

On whether a project declaring something unsupported lowers severity: *on its own, no* — a project cannot declare a defect away. But the startup failure is **loud** (a `CreateTable` against existing tables), not silent, and can only occur on a developer machine holding a stale local file, because nothing shipped on the old history. That is not "a path reachable in normal use" — and if it were, the token would be S1, not S2. **Severity moved because the record's substance genuinely changed:** B1's fix removed the false mechanism (silent skip, quiet corruption) and the residue is smaller. Severity tracking substance is correct behaviour. `risk: high → medium` follows — the suggested fix is now documentation, a startup guard, a comment update and a CI check.
