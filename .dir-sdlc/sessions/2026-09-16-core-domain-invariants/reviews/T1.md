## The near-miss, confirmed rather than taken on trust

The implementer self-reported that its null test would have been **inert** if written to criterion 3's literal
text alone. The reviewer reproduced it and confirmed it.

With the guard removed, the null case reaches `_outline.AddRange(null)`, which throws `ArgumentNullException`
of its own accord — with `ParamName` `"collection"`. So `ThrowExactly<ArgumentNullException>()` **passes
vacuously against unguarded code**. The observed discrimination failure was:

```
Expected exception with parameter name "outline", but found "collection".
```

The `.WithParameterName("outline")` assertion at `AreaOutlineTests.cs:98` is therefore the entire source of
that test's power. It is present, and the test went red as required, so criterion 3's purpose is served.

**Criterion 3 as written did not mandate the parameter-name assertion.** A literal reading of it yields a test
that cannot fail. This was caught by the implementer, not by the criterion — which is worth recording, because
the criterion was orchestrator-authored and it is the third orchestrator-authored criterion defect across this
session and its two predecessors.

## Advisory findings

Advisory findings trigger no revision round. Collected at Gate 3.

1. **`AreaOutlineTests.cs:97-98` — the null test's power rests on one line.** Dropping `.WithParameterName("outline")`
   would silently make the test vacuous, because `List<T>.AddRange(null)` throws the same exception type from
   downstream. Worth a comment at the assertion recording why the parameter name is load-bearing.
   *(Group: test and CI concerns.)*
2. **`AreaOutlineTests.cs:163-164` — `UpdateAreaOutline_WithThreeSegments_Succeeds` asserts `HaveCount(3)`
   rather than `Equal(...)` by value**, so it would not catch a `SetOutline` that stored the wrong three
   segments. Criterion 3 asked only for the count, so the criterion is met as specified; the observation is
   about the criterion, not the code. *(Group: correctness risks.)*
