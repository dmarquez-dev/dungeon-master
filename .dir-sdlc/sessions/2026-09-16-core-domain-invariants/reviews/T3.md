## (a) Ruling on the contract deviation — substance met, form only, not a finding

Contract §3 sketches the validating helper with camelCase parameters (`kind, ctrl1, ctrl2`). **That form does
not compile in this repository.** The implementer named the helper's parameters `Kind`, `Ctrl1`, `Ctrl2`
instead, so `nameof(Ctrl1)` binds to a real parameter with the casing §3's table demands, and judged this form
rather than substance without escalating.

**The reviewer ruled that correct, and verified the claim rather than accepting it**: it restored the camelCase
parameters with `nameof(Ctrl1)`/`nameof(Ctrl2)` intact and built `DungeonMaster.Domain` — **4 errors, `CA2208`**,
at `:49`, `:56`, `:65`, `:72`, wording verbatim as reported including *"the exact casing as declared on the
method."*

What §3 *binds* is its table: exact type `ArgumentException`, `ParamName` exactly `Ctrl1`/`Ctrl2`. Both hold,
proven by seven passing assertions. The sketch is introduced as *"The construction form that satisfies this"*
and its body is the placeholder `{ /* throw per the table, else return kind */ }` — it never claims its
parameter casing is binding, and the table demands the opposite casing. Escalating would have asked the user to
choose between a contract table and a build error when only one outcome satisfies both.

**This is an orchestrator defect, recorded as such.** The contract was frozen carrying a code sketch that does
not build in this repository. It was rung-4 judgment presented in the authoritative form of worked code, which
is exactly the kind of detail a reader trusts and should not have. The correct contract pins the observable
behaviour — type and `ParamName` — and leaves the construction form to the implementer. The comment at
`PathSegment.cs:37-39` records the reason in the code, which is the right home for it.

## (b) The exception-type observation — reproduced, not accepted

This was the session's one deliberately-unpinned unknown: criterion 4 forbade guessing whether
`System.Text.Json` surfaces a constructor `ArgumentException` directly or wraps it in a `JsonException`, and
required the implementer to run it and pin what it saw.

**It surfaces directly, unwrapped.** The reviewer confirmed it in two directions:

- **Forward**: `Deserialize_CorruptRowWhoseCubicBezierHasANullCtrl2_Throws` passes with
  `ThrowExactly<ArgumentException>().Which.ParamName == "Ctrl2"`. `ThrowExactly` admits no derived type and no
  wrapper, and a `JsonException` carries no `ParamName` — so a wrapped exception could not satisfy this
  assertion. That is precisely the failure mode the criterion guards against, and it is excluded.
- **Injected defect**: with only the `CubicBezier`/`Ctrl2` throw removed from production code and the tests
  held fixed, that test failed with *"Expected System.ArgumentException, but no exception was thrown"* while
  the positive control still passed. The pass is caused by the guard, not by incidental JSON behaviour.

## Advisory findings

Advisory findings trigger no revision round. Collected at Gate 3.

1. **`PathSegment.cs:61` — `ValidateControlPoints` routes every non-`CubicBezier` kind into the "must not carry
   control points" branch via a bare `else`.** `PathSegmentKind` has exactly two members, so this is
   behaviourally exact today; a future third kind would silently inherit `Line` semantics. An explicit
   `else if (Kind == PathSegmentKind.Line)` would make that a compile-visible decision. Criterion 1's `Line`
   direction is satisfied as written. *(Group: correctness risks.)*
2. **`PathSegmentJsonRoundTripTests.JsonOptions` replicates `AreaConfiguration.cs:16`'s options rather than
   referencing them**, so a future change to the production options would not propagate to the test. Criterion 4
   asked for "the shape `AreaConfiguration` uses" and the shape matches exactly, so the criterion is met; this
   is a drift risk only. *(Group: test and CI concerns.)*
