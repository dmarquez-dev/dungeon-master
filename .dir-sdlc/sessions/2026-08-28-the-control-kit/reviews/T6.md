## The two observed negatives

**Criterion 2 — `MASTER-161`'s remedy is structurally correct and practically inert, and the attach point is the likely fault.** User observation, 2026-09-01: no hand cursor over the floor or area **card body or name text**. **But the buttons and icons in the same controls do work, and so does "+ Add Area".** So `HandCursorBehavior` is not broken in the sidebar — it takes effect on `Button` elements and fails on the `VerticalStackLayout` card body and the name `Label`.

That narrows the diagnosis. `DmCard` attaches the behavior to **itself**, the `ContentView` root (`DmCard.xaml.cs:108`), and Session 4 observed that working on dungeon-list cards. T6 attached to an **inner `VerticalStackLayout`**. The probable remedy is to attach at the root `Border`/`ContentView` as `DmCard` does, rather than to an inner layout — a cheap, specific lead, not an open-ended investigation.

The orchestrator initially generalised the user's report to "inert throughout the sidebar", which the user corrected. The narrower fact is the useful one and is what goes to T9.

**Criterion 11 — the drag cannot be observed because the feature is unreachable.** User observation, 2026-09-01: floor reordering cannot be performed at all, because the overlay scrollbar renders on top of the drag glyph.

Mechanism, confirmed in the tree by the orchestrator: the drag handle is `Grid.Column="4"` — the last column, hard against the card's right edge (`FloorSidebarItem.xaml:164-171`) — and the floor list sits inside a `ScrollView` (`DungeonDetailPage.xaml:667`). WinUI overlay scrollbars draw over content at exactly that edge, so whenever the list is long enough to scroll, the scrollbar covers the only affordance for reordering.

**Pre-existing.** T6 changed neither the column layout nor the `ScrollView`. This also retroactively explains T6's synthetic-`SendInput` failure, which reproduced identically on the unchanged baseline: the apparatus was not the only problem — the target is genuinely unreachable.

**Consequence for `MASTER-098`:** the `DragOver` paint path is the one behaviour this diff rewrote (`OnDragOver` previously set only `Stroke`; it now enters a state setting both `Stroke` and `BackgroundColor`) and it **cannot be observed by anyone** until the scrollbar defect is fixed. `MASTER-098` therefore records as **`part done`** — the four verified states are solid, the drag state is unverifiable for reasons outside this task.

## Findings the reviewer produced

- **The `CommonStates` naming is load-bearing, not stylistic.** MAUI's `VisualElement.ChangeVisualState()` drives the `CommonStates` group itself on enabled, focus and pointer-over transitions. Had these groups been named `CommonStates`, every internal `GoToState` call would have targeted the same group and evicted `Selected`/`Expanded` — a row would lose its gold border the moment the pointer touched it, which is exactly what the old `if (!_isSelected)` guards prevented. `SelectionStates`/`FloorStates` is the correct call.
- **T6's "criterion 13 mis-cites" claim is REFUTED — and this correction was headed for the audit record.** Criterion 13 says the files appear in `MarginPendingMigration` **or** `StrokePendingMigration`, and `Relative("Controls", "AreaSidebarItem", "AreaSidebarItem.xaml")` genuinely is in `MarginPendingMigration` at `GeometryScaleTests.cs:291`. The criterion is correct as written; T6 read it as a claim about the stroke list alone. **T9 must not carry this correction.**
- **The `Color->Brush` widening entry is at `TokenTypeMatchesTargetPropertyTests.cs:179`, not `:180`.** Substance right, line number off by one.
- **`IsSelected` is never used as a binding target.** The item template sets `Area` and the five commands but not `IsSelected`; selection still arrives imperatively through `SetAreaEditing` walking `AreaContainer.Children`. Satisfies criteria 3 and 6 as written — `SetAreaEditing` is explicitly blessed there — but the "valid binding target" rationale in the doc comment is aspirational rather than exercised.
- **The `FloorItem.Areas` binding is safe, and why is worth recording.** `FloorItem` is a record with `IReadOnlyList<AreaItem> Areas`, replaced wholesale rather than mutated, so `BindableLayout.ItemsSource="{Binding Floor.Areas, …}"` re-evaluates on every `Floor` assignment exactly where `RebuildAreas` used to run. Had `Areas` been a mutable non-observable list, this conversion would have silently stopped updating.
