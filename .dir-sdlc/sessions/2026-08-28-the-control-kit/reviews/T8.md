## The defect T8 caught in its own first attempt

It first implemented the subtitle rule with two `DataTrigger`s bound `{Binding Subtitle, Source={x:Reference Root}}`. **It built at 0/0 and looked correct.** Probing against a rebuilt baseline showed it broken:

| Build | card 2 ("T5 Async Guard Check", empty description) |
|---|---|
| baseline `DmCard` (byte copy, rebuilt) | ListItem `1381x83`, **no** subtitle `Text` element |
| its `DataTrigger` version | ListItem `1381x96`, `[Text] … 1161x29` — **a visible empty row** |
| its property `Trigger` version | ListItem `1381x83`, no subtitle element — matches baseline |

The `DataTrigger`s never fired; property `Trigger`s on the label's already-bound `Text` need no source resolution of their own and do fire.

**The middle row is what makes this evidence rather than decoration** — it demonstrates the observation would have *caught* the failure, not merely coexisted with success. A build-clean, plausible-looking XAML change that silently adds a blank row to every subtitle-less card is unreachable by any test in this repository and invisible in a diff review.

## Advisories carried to Gate 3

**A1 — T8's `OnPointerExited` correction is aimed at the wrong document, and T9 must not act on it.** T8 listed the reachability point as a correction to `UIKIT-019`. But `docs/audit/04-app-controls-and-theme.md:757-761` **already says it verbatim**: *"Today that is harmless because the call is guarded by `!_isEditing`, but the guard and the mutation are in different methods."* Verified independently by the orchestrator.

The overstatement is in **this session's own manifest criterion 2**, which paraphrased it as "clears `_isEditing` even while the input still holds focus". T8's underlying finding is correct — base `:336-339` is `if (!_isEditing) { ClearFocusGlow(); }`, so the write was provably a no-op on that path — but **`UIKIT-019` needs no amendment**. Not a `contradicts`: the record is accurate, so no scoped work moves.

This is the **second** would-be record correction refuted in this session, after T6's criterion 13 claim. Both were caught by a reviewer reading the cited source rather than the citing claim.

**A2 — the two opposite `MASTER-077` resolutions are principled, not arbitrary.** They fall out of one consistent rule: *the mechanism that can express the whole rule wins.* `DisplayLabel.TextColor` is a **switch** on emptiness that a one-way binding cannot express → imperative wins. `TitleLabel.Text` is a plain **pass-through** a binding expresses completely → binding wins. `SubtitleLabel.IsVisible` is a two-case **predicate** markup triggers express → markup wins. The rule is stated at each site. Taking the branch `UIKIT-007` did not name for `DmFlagBanner` is the better call on its own facts — the record's branch leaves two imperative writers, T8's leaves one owner — and it is documented as a deliberate departure.

**A3 — the temporary experiment reverted byte-clean.** T8 made `DmFlagBanner`'s dead `TitleEditor` visible to observe the placeholder treatment (unreachable through the notebook, which rejects empty names), then reverted. `git diff --stat 795c839 -- …/DmFlagBanner.xaml` is empty and the file is absent from `git status --porcelain` — **byte-level proof against the base blob, not a visual comparison**.

**A4 — constructor `SyncDisplay(Text)` is safe against the lazy `defaultValueCreator`.** It reads `TextColor` after `InitializeComponent`, strictly *later* than the XAML binding that previously resolved during it, so the deliberate laziness protecting against `Application.Current.Resources` not yet existing is not weakened.
