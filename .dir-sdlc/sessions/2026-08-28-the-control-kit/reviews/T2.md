## The reversal, and why it stands

`MASTER-159` claims `DmCard`'s trailing content never renders. **It does.** T2's first probe reproduced the audit's symptom near-verbatim — 27-element tree, no buttons, card does not lighten — and was **defective**: DPI-unaware `SetCursorPos` at 125% display scaling, plus a wrong `INPUT` struct size (`SendInput` → 0, `GetLastError()=87`). T2 caught it with an **apparatus control** on an unrelated `PointerGestureRecognizer` (the FAB), which also never fired, isolating the probe rather than the control. With `SetProcessDPIAware()` and a corrected struct, the defect does not reproduce.

The entry's stated mechanism is independently falsified. The project sets `MauiXamlInflator=SourceGen`, so the `DataTemplate` body is compiled C#, and `Views_DungeonListPage_DungeonListPage.xaml.xsg.cs:848` contains, inside the factory lambda:

```csharp
dmCard.SetValue(global::DungeonMaster.App.Controls.DmCard.TrailingContentProperty, horizontalStackLayout);
```

Verified independently by the orchestrator. Runtime logging recorded the callback running once per card with `presenterContent` set.

This is the **same class of apparatus failure the audit itself documented for `MASTER-039`** (`00-master-index.md:419`), where a cursor probe reported ARROW at every point on both the changed and unchanged builds.

**One inconsistency T2 flagged rather than smoothed over:** the entry claims the card lightens and `PointerOver` applies while no button appears. Those halves cannot both hold — if `PointerOver` applied, `HoverEntered` ran, which reveals the presenter in the same instant. Likely a human observation and an automated capture taken at different moments. T2 did not witness Session 4's apparatus and declined to assert what it was.

The reviewer corroborated the phase ordering from the artifact timeline independently: 27/30-element trees through 11:24, 34-element post-change trees from 11:35.

## The E2 fix

`TrailingPresenter` is hidden by `Opacity` rather than `IsVisible`, so it is laid out and its buttons have platform views at all times. `TrackTrailingFocus` walks the assigned content via `IVisualTreeElement.GetVisualChildren()` and subscribes `Focused`/`Unfocused` on every descendant `VisualElement`; `UpdateTrailingReveal()` reveals when `_pointerOver || _focusedDescendants > 0`. `OnTrailingDescendantUnfocused` re-evaluates on the next dispatcher turn, because tabbing between two trailing buttons raises `Unfocused` before `Focused` and the count would dip to zero in between.

`InputTransparent` is gated on the reveal state — `true` while hidden, `false` while revealed — because the presenter now sits permanently over the right-hand end of the card, above the card's own `TapGestureRecognizer` (`DungeonListPage.xaml:46`), and because the 0-floor card's always-present `BoxView` would otherwise raise "Add at least one floor before starting a session" over a region showing nothing.

**T2 was wrong about that trade and the tree corrected it.** It expected `InputTransparent` to map to `IsHitTestVisible=false` on Windows and drop the buttons from the tab order, defeating the change. Measured instead: focus ring unchanged at six stops, and the buttons still activate on both routes. It verified the hard case specifically — a **real mouse moved onto the Edit button from outside the card and physically clicked**, since UIA `Invoke` bypasses hit-testing and would have masked a failure. Card-body physical click at 30% width still navigates; the reviewer reproduced that.

**A finding that changes what "reachable" means, not a defect:** Tab alone never reaches the *second* card — `CollectionView` is a single tab stop and moves between items with arrow keys, standard WinUI `ItemsView` behaviour. The route is Tab into the list, arrow to the card, Tab through its actions. Card 1's `StartSessionButton` is correctly skipped, being disabled at 0 floors.

## Advisories carried to Gate 3

- **A1 — hidden trailing controls stay UIA-exposed with `IsOffscreen=False`.** All six trailing buttons are present with `off=False` while `Opacity` is 0. Criterion 12's operative clause holds: focus never *rests* invisibly, because the `Focused` handler reveals the region first, and no reveal-on-focus design can work unless the target is a focus candidate beforehand. The residue is that a screen-reader user in scan mode, without moving focus, encounters six action buttons a sighted user sees no hint of, and `IsOffscreen` no longer tracks visual presence. **Fold into the new rank-162 entry.**
- **A2 — `StartSessionButton` is now a permanent tab stop.** TAB 3 on a floored dungeon, and enabled, so a keyboard user can activate an unwired no-op. Contract invariant 5 anticipates the fix making the button visible and requires only that the comment stay accurate, which it does. Flagged because the fix changes who encounters it. **Fold into the new rank-162 entry.**
- **A3 — `TrackTrailingFocus` resets `_focusedDescendants = 0` on every `TrailingContent` change.** Under `CollectionView` recycling, a card re-templated while focus sits in its trailing region would desync the count. Not reproducible with the two-item fixture; not in scope.
- **A4 — descendant subscription is a one-time snapshot.** `ForEachVisualElement` walks once at content assignment; children added later are never tracked. Fine for the sole consumer, a static `HorizontalStackLayout`.
- **A5 — citation off by one.** The report cites `AreaSidebarItem.xaml:93`; the element spans `:92-95`.
