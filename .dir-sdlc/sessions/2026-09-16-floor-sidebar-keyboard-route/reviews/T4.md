## The perturbation demonstration — sound, with a limit the reviewer named

T4 went beyond its criteria and perturbed its own **expected literals** (`"Button"`→`"Label"`, the hint to a
`"Ctrl+Up"` form) to show the markup assertions are not vacuous. The reviewer ruled it **sound**: the
unperturbed assertion passes and the perturbed one fails, so the actual value is one specific string rather
than whatever the expectation happens to say — which is exactly the tautology it rules out.

**The limit, worth keeping:** perturbing the expectation varies the **wrong side**. It proves expected ≠
actual under perturbation; it does not by itself prove the actual side is *derived from the markup file*
rather than computed independently — **a hard-coded reader would behave identically.** Here the residual risk
is nil on inspection (`Attribute()` reads the `XDocument` from `ThemeSource.AppDocuments()`, and
`TheScanReachesTheElementsItAssertsAbout` pins that the scan reaches exactly one element), so the conclusion
stands. The strictly stronger form perturbs the **input**: change the XAML and watch the unperturbed test
redden.

### Where the reviewer corrected T4, and it is the most valuable thing in this review

T4 disclosed that it **never observed the pre-existing `"Label"` failure** — its first run came after both
files were written — and argued the perturbation run was *"the stronger evidence anyway"*.

**The disclosure is correct and costs nothing. The ranking is inverted, and the reviewer said so.**

For these two markup assertions the missed original red-to-green **was** the input-side demonstration: before
T3 converted the element, the markup genuinely read `Label` and carried no keyboard hint, so the unperturbed
new assertions would have failed against **real, un-doctored input**. That is strictly stronger than
perturbing the expectation, for the reason above — it varies the input and holds the test fixed.

It changes no verdict: criterion 4 scopes the required demonstration to `FloorReorderKeys`, and there T4 did
perform a genuine input-side injection, which the reviewer reproduced. But the **reasoning** should not be
reused, which is why it is recorded here.

## The untested gate — T4's recommendation, and the reviewer's correction to it

T4 was asked to recommend coverage and forbidden to build it. It reported the corrected count:
`grep -rn "ContainsKeyboardFocus\|FocusReorderAffordance"` over `src` returns **9 lines — 6 production, 3
test-project doc-comment prose it added this round, no assertions.** The orchestrator's brief had said five;
the sixth is a XAML comment.

Its ranked recommendation:

1. **A test in `DungeonMaster.App.Tests/Views/`** covering the recursion **at depth** (a focused descendant
   in the area list, not a direct child — the part most likely to break under a later template change and the
   part no reviewer can eyeball), an unfocused card reporting false, and `FocusReorderAffordance()` landing
   on `ExpandToggle`. Precedent: `FloorReorderDropRoundTripTests` in that same directory.
2. **Extend `FloorSidebarAutomationTests`** in the Appium project for the route end to end — the only route
   that tests what O1 actually validated.
3. Leave it and record the gap — which T4 itself said should not be treated as closing anything.

**T4 attached a caveat to its own top recommendation, and the reviewer disproved it.** T4 warned that no
precedent exists for driving focus in a test and that `VisualElement.IsFocused` is read-only, so the test
might need reflection against a private property key — coupling it to MAUI internals and collapsing its
value.

**The reviewer reflected over `Microsoft.Maui.Controls.dll` as built in this worktree.** `IsFocused` indeed
has **no setter** (`CanWrite=False`) — but **`VisualElement.IsFocusedPropertyKey` is a public static
`BindablePropertyKey`, and `BindableObject.SetValue(BindablePropertyKey, object)` is a public overload.** So
a test can write `descendant.SetValue(VisualElement.IsFocusedPropertyKey, true)`: **public API, no
reflection, no internals coupling.** `HasFocusedDescendant` (`FloorSidebarItem.xaml.cs:342`) reads
`VisualElement { IsFocused: true }` off the visual tree, which is precisely that input.

**The recursion-at-depth half is therefore cheap to write.** `FocusReorderAffordance()`'s own `Focus()` call
still needs a platform handler and remains observation territory — that half of the caveat stands.
